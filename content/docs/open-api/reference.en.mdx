Parse success responses per endpoint: catalog queries, /me, and sync status use `data`; publishing, whoami, and deletion use `result`; title matching directly returns `version`, `decision`, and `candidates`. Anime preview returns a top-level `previewUrl`.

In title-match responses, `candidates[].matchScore` is an ordinal rank score, not a percentage. When `evidenceSummary.matchClass` is exact, structured_exact, compact or base, it is 100, 95, 90 or 80. A candidate found only by recall (`strict_recall`, `fuzzy_recall`) scores 1–70, lower when a word differs in spelling or one word is ignored. A candidate added only for series completion scores 0. Recall candidates with equal scores are ordered by `textMatch`, which is also ordinal only.

Application JSON errors contain `ok: false` and `error.code`, `error.message`, and `error.requestId`. `reason`, `retryable`, `retryAfterMs`, and `details` are optional. A missing retryable flag does not authorize retries. Public RSS errors are usually plain text. Torznab protocol errors are XML and may have HTTP 200. Edge blocks may be HTML. Check status and Content-Type before parsing.

Before publishing, GET the same endpoint and check groupSlug and scopes. A publish receipt guarantees releaseId and revision, with an optional torrentObjectId; it does not include group identity or fileSize. Use rel_* or orel_* as required. Group filters usually take a slug; other-category RSS groupId takes an organization ID.

## Publishing retries and republishing after deletion

Use an `Idempotency-Key` for each normal publish request. Keep the same value when retrying the same content with the same API Key and publish endpoint. The value must contain 1–256 characters after trimming. A missing or empty value starts a new command and provides no command replay guarantee. A value longer than 256 characters returns `422 VALIDATION_ERROR` with `error.details` set to `{ "header": "Idempotency-Key", "maxLength": 256 }`; the server does not read the request body and publishes nothing. Cross-origin browser preflight currently does not allow this header; use a server-side client when you need this guarantee.

Retrying a successful command returns its original `releaseId` and `revision` without publishing again. This remains true after that release has been deleted: the old receipt does not restore the release. To intentionally publish the same torrent again after deletion, use a new `Idempotency-Key`.

From first acceptance, an `Idempotency-Key` is bound to the complete request. Use a new key when switching between publication and preview, or changing resource content, Nyaa options, an explicit publication timestamp, or the uploaded file. Upload completion and an existing receipt do not bypass an established binding; changing the request under the same key returns `409 CONFLICT`.

An unfinished request uploaded before the upgrade may lack a complete binding. In that case it returns `409 CONFLICT` with `error.reason` set to `legacy_request_binding_missing`. Submit the complete request with a new key. Completed legacy requests retain their existing receipt replay behavior.

When the group already has a release of the same anime with the same episode key, version, subtitle type, resolution, languages, and torrent, publishing it again returns `409 CONFLICT` with `error.reason` set to `RELEASE_VERSION_EXISTS`. That torrent is already published as this version, and retrying with a new key won't succeed either.

A stored torrent can back only one release. When the `torrentStorageId` of a JSON request names a torrent that another anime release, an other release, or another user's unexpired preview already uses, both publishing and previewing return `409 CONFLICT` with `error.reason` set to `TORRENT_IN_USE`, and nothing is written; upload the torrent file with multipart instead. The same publisher republishing an anime release with the same content still gets the existing release, and a torrent you previewed yourself can be published directly. Once it is published, its previews stop working.

Publishing returns `403 FORBIDDEN` when the group's status is not Active (it is Inactive or Suspended), or when the key is revoked while the request is running.

When a member leaves or is removed from the group, their API keys of that group are revoked at the same time, and later requests with those keys return `401`. The keys stay revoked even if the member joins the group again; create a new key. Changing a member's role does not affect their keys.

A magnet link in the request must carry a v1 infohash: `xt=urn:btih:` followed by 40 hexadecimal or 32 base32 characters. The `xt` key is case-insensitive, so `XT=urn:btih:…` is accepted too, and a hybrid magnet that also carries `urn:btmh` is accepted even when `urn:btmh` comes before `urn:btih`.

These requests return `422 VALIDATION_ERROR`, and `error.message` names the rule they break:

- an empty episode key;
- `episode` and `episodeKey` that disagree;
- a magnet link with no `xt=urn:btih`, or whose btih is not a valid v1 infohash, or a torrent whose magnet link carries no infohash;
- a request with no torrent that also lacks a file size above 0 or an infohash;
- a `torrentStorageId` that does not exist or belongs to another group;
- a field over its length limit, with the fields listed in `error.details.fieldErrors`.

Retrying these requests unchanged or with a new key won't succeed.

The `Content-Length` header may contain only digits. When it has anything else (such as `1e3`, `1.5` or `-1`), publishing returns `400 INVALID_BODY` with `error.message` set to `Invalid Content-Length`; the body is not read and nothing is published. Some of these values are refused before the request reaches the application; that answer is a `400` too, but its body may not be JSON. A body that cannot be read to the end (for example, the upload breaks off) returns `400 INVALID_BODY` with `error.message` set to `Request body could not be read`, instead of `500 UPLOAD_FAILED`, and nothing is published. A body over the size limit still returns `413 SIZE_EXCEEDED`; see [Rate limits and parameter bounds](/en/docs/open-api/limits) for the limits.

A numeric episode key is stored in one form: without leading zeros, and a decimal also without trailing zeros. `05.5` and `5.50` are both stored as `5.5`, `01` as `1`, and `01-13` as `1-13`.

When an anime release is published without `resolution`, the resolution is read only from the parts of the title that state one: `1080p`, `1080P` or `1080i`, a width × height such as `1920x1080` or `3840x2160`, and `4K` as a word of its own. `2160p` and `3840x2160` are read as `2160p`; only a title that says `4K` gets `4K`. Episode numbers, bare numbers without `p` or `i` (such as `1080`, `720` or `2160`), digits inside a checksum, and a `4K` inside a word (such as `Show4Kids`) are not a resolution, so `[Group] One Piece - 1080 [720p].mkv` is read as `720p`. When the title states no resolution, the torrent's internal name is read by the same rule, and if that has none either, the resolution is `1080p`.

POST and GET (whoami) on the publish endpoints are counted per source before the key is checked, including requests whose key is invalid; over the limit, the answer is `429` and the key is not checked. whoami is counted separately and does not spend the publishing allowance. See [Rate limits and parameter bounds](/en/docs/open-api/limits) for the numbers.

For `429 RATE_LIMIT_EXCEEDED`, wait for the number of seconds in `Retry-After`. A busy publishing service, a rate limiter that temporarily cannot count, or an unconfirmed upload result can return `503 SERVICE_UNAVAILABLE`; when the rate limiter cannot count, `Retry-After` is always 15. When a `503` includes `Retry-After`, wait and retry the same request with its original key. Without that header, check existing releases and keep `error.requestId` first. A failure or lost connection does not prove that nothing was written. Avoid immediate batch retries or repeatedly switching keys for an uncertain result.

## Refused deletions

`DELETE /api/releases/{releaseId}` returns `404 NOT_FOUND` with `error.message` set to `Release not found` when the release does not exist, belongs to another group, or was published by another member of the same group and the key belongs to a plain member. These cases return exactly the same response. A plain member's key can delete only that member's own releases; an owner's or admin's key can delete any release of the group.

Deletion returns `403 FORBIDDEN` and deletes nothing when the group's status is not Active (it is Inactive or Suspended), or when the key is revoked while the request is running. Once a member has left or been removed from the group, their keys of that group are revoked and a deletion returns `401`.
